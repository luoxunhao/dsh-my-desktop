# Spec — 阶段 6：恢复页 UI 全套对齐（React + Vite + Tailwind + Base UI）

**Status:** ready-for-agent
**Slug:** `recovery-ui-alignment`
**Depends on:** 阶段 1–5（均已落地并验证）

---

## Problem Statement

用户的应用无法启动时，恢复助手是他们唯一的出路。当前恢复页
（`assets/recovery.html`，18 KB 单文件、原生 JS + 手写 CSS）已经能打开、能卸载出问题的
插件、能看启动日志——但它的**视觉与交互与参考实现 `dsh-desktop` 不一致**，而且缺少
`dsh-desktop` 恢复页已具备的能力：

- **没有 checkpoint 回滚入口**：阶段 3 已经实现了完整的健康启动快照（3 个滚动槽、
  skip marker、原子替换），但用户在恢复页上**看不到也用不到**它——后端有、UI 没有。
- **没有 profile 切换入口**：`desktopProfiles` 后端早已存在（列/建/删/选，
  设置插件里也已有 UI），但恢复页里没有，用户在恢复态下无法换一个能用的 profile。
- **没有两阶段确认**：`dsh-desktop` 对破坏性操作（卸载插件、回滚快照）要求
  preview → execute 两步，避免误点造成不可逆后果。我们目前是**一步直达**。

结果是：**阶段 3 那套精心实现、经过评审加固的快照能力，对用户不可见。**

## Solution

按 `dsh-desktop` 的技术栈重建恢复页，使其在**视觉与结构上与参考实现同构**，并接上
我们已经实现但尚未暴露的后端能力。

用户视角的改变：

- 恢复页长成 `dsh-desktop` 的样子（同一套组件、同一套配色、同一套布局）
- 能**看到 3 个快照槽**，看到每个槽的捕获时间、桌面端版本、文件数、大小，
  并选择任意一个回滚
- 能**列出并切换 profile**，切到一个能启动的 profile 后重启
- 破坏性操作（卸载插件、回滚快照）**先预览再执行**，确认框里能看到影响面

### 为什么值得引入整套前端工具链

启动器目前是**零前端框架**：6 个手写原生 HTML、零构建步骤、直接拷进包。
`react` 虽在 `devDependencies` 里但**全仓零 import**。

要让恢复页与参考实现"包括界面样式"一致，就绕不开 Tailwind——参考页的视觉
**主要由 Tailwind class 表达**（`App.tsx` 263 行密集 JSX）。用原生 CSS 复刻等于
逐条翻译每个 class，工作量大且视觉必然漂移。

**这是一次有意的取舍**：用"启动器从零框架变成需要维护前端工具链"换取"真正的视觉一致"。
用户已明确选择这条路。

## User Stories

### 加载与外观

1. 作为 DSH My Desktop 用户，我希望恢复助手打开时**立即显示**而不是空白等待，
   以便在应用起不来时立刻看到我能做什么
2. 作为用户，我希望恢复页的**标题、配色、按钮样式**与桌面应用的其它窗口一致，
   以便它看起来是同一个产品的一部分
3. 作为用户，我希望恢复页在**浅色和深色主题**下都正常显示，以便跟随我的系统设置
4. 作为用户，我希望恢复页在**窄窗口**下仍可用（标签页可横向滚动、卡片不溢出），
   以便在小屏笔记本上排障
5. 作为用户，我希望恢复页**不发起任何网络请求**，以便在离线环境也能排障

### 恢复原因

6. 作为用户，我希望恢复页顶部说明**为什么进入了恢复模式**（是插件的锅？还是我自己
   点进来的？），以便决定下一步做什么
7. 作为因插件不兼容而启动失败的用户，我希望看到**导致失败的插件名**，
   以便判断该卸载哪个
8. 作为用户，我希望看到**当前 profile 名与其目录路径**，以便在手动排查时知道该看哪个文件夹
9. 作为用户，我希望看到**启动失败时的错误详情**，以便搜索或上报
10. 作为用户，我希望失败详情**可滚动**（长堆栈不会撑破布局），以便完整阅读

### 快速恢复

11. 作为用户，我希望有一个"快速恢复"页**汇总所有可用的修复手段**，
   以便不必先搞懂每个标签页是干什么的
12. 作为用户，我希望快速恢复页说明**每种手段适合什么场景**，
   以便选对工具而不是乱试

### 插件管理

13. 作为用户，我希望看到**当前 profile 的全部插件清单**，以便知道装了什么
14. 作为用户，我希望看到每个插件是**核心 / profile 依赖 / 外部**，以便判断能否安全卸载
15. 作为用户，我希望看到插件**是被禁用还是启用**，以便知道它是否还在生效
16. 作为用户，我希望**只能卸载标记为可卸载的插件**（核心插件不提供卸载按钮），
   以便不会把应用搞坏
17. 作为用户，我希望卸载插件前**先看到确认预览**（显示插件名与影响），以便避免误点
18. 作为用户，我希望卸载后能**恢复**它，以便发现卸错了还能救回来
19. 作为用户，我希望能把某个插件**保留在隔离状态**，以便暂时禁用它而不删除

### 快照回滚

20. 作为用户，我希望恢复页有独立的**回滚标签页**，以便集中处理配置损坏
21. 作为用户，我希望看到**3 个快照槽**（包括空槽），以便知道我还剩几个可用恢复点
22. 作为用户，我希望每个有内容的槽显示**捕获时间**，以便选一个配置还正常的时间点
23. 作为用户，我希望看到快照的**桌面端版本**，以便避免回滚到跨版本的配置
24. 作为用户，我希望看到快照**包含的文件数与总大小**，以便了解回滚的影响面
25. 作为用户，我希望看到**哪些文件与当前不同**（差异检查），
   以便知道回滚会改动什么
26. 作为用户，我希望回滚前**先预览**（显示槽位、时间、将改动的文件清单），
   以便确认这是我想回滚到的点
27. 作为用户，我希望预览有**有效期**，以便过期的确认不会被误执行
28. 作为用户，我希望预览**只能执行一次**，以便重复点击不会重复回滚
29. 作为用户，我希望回滚后**改动 package.json / lock 文件时**提示需要重新物化依赖，
   以便我的应用能真正恢复可用
30. 作为用户，我希望回滚后**首次启动不会覆盖**我选中的那个恢复点，
   以便在验证能否启动时不会毁掉它
31. 作为用户，我希望快照**损坏时其它槽仍可用**，以便一个坏文件不会让我失去所有恢复点
32. 作为用户，我希望在**没有任何可用快照**时看到明确说明，而不是空白区域

### Profile 切换

33. 作为用户，我希望恢复页能**列出所有 profile**，以便换一个能启动的
34. 作为用户，我希望看到**哪个是当前 profile**，以便知道现在用的是哪个
35. 作为用户，我希望看到每个 profile **是否可切换**，以便知道哪些是可用的
36. 作为用户，我希望**切换 profile 后能重启**到新的 profile，以便真正生效
37. 作为用户，我希望**当前 profile 不能被删除**，以便不会把自己踢出去

### 诊断

38. 作为用户，我希望查看**启动日志**，以便定位 DSH 为什么没起来
39. 作为用户，我希望**导出诊断信息**并在导出后能**打开所在文件夹**，
   以便发给别人分析
40. 作为用户，我希望导出前知道**诊断包含什么**（日志、崩溃转储、系统信息），
   以便判断隐私风险

### 危险操作与退出

41. 作为用户，我希望**无法访问的标签页显示明确说明**（而非空白或假 UI），
   以便我知道这个能力不存在而不是坏了
42. 作为用户，我希望有**重启**按钮退回正常工作台，以便修好之后回到应用
43. 作为用户，我希望有**退出**按钮，以便不想修时直接关掉
44. 作为用户，我希望**忙碌时界面被禁用**并显示进度，以便不会重复触发操作
45. 作为用户，我希望操作**失败时看到原因**而不是静默失败，以便知道该怎么办

### 数据目录管理

46. 作为用户，我希望看到**当前数据目录的完整路径**，以便知道我的数据实际存在哪里
47. 作为用户，我希望知道**这个目录是怎么来的**（系统默认 / 环境变量 / 我自己设的），
    以便理解为什么改不动它
48. 作为用户，当 `DSH_HOME` 环境变量已设时，我希望页面**明确告诉我它被环境变量接管了**，
    以便不会白改半天以为没生效
49. 作为用户，我希望**把数据目录改成另一个位置**，以便数据放在损坏磁盘上时能救回来
50. 作为用户，我希望改目录前**能浏览选择一个目录**，以便不必手打长路径
51. 作为用户，我希望**目标不存在时被明确拒绝**（而不是接受一个不存在的路径），
    以便不会把应用指向空目录
52. 作为用户，我希望**符号链接被拒绝**，以便不会因为一个链接把数据写到意外的地方
53. 作为用户，我希望**危险目标被拒绝**（文件系统根、应用自己的状态目录），
    以便不会把应用搞成不可用
54. 作为用户，我希望页面上明确说明**数据不会自动搬过去**，
    以便我不会以为新目录里已经有我的数据
55. 作为用户，我希望改完目录后**能重启使其生效**，以便新位置真正被使用
56. 作为用户，我希望能把数据目录**恢复成系统默认**，以便改错了能退回
57. 作为用户，我希望在我**没改过目录时看不到"恢复默认"按钮**，以便界面不出现无意义的操作

### 出厂重置

58. 作为用户，我希望有一个**出厂重置**入口，以便配置坏到无法逐个修复时能从头开始
59. 作为用户，我希望页面**明确说明这是不可逆的**，以便我不会随手点
60. 作为用户，我希望重置前**先看到将被清除的内容摘要**（数据目录、profile 数量），
    以便确认我删的是对的东西
61. 作为用户，我希望重置**先预览再执行**（两阶段确认），以便误点不会立刻造成损失
62. 作为用户，我希望重置**拒绝在文件系统根上执行**，以便不会误删整块盘
63. 作为用户，我希望重置**拒绝在包含应用自身状态的目录上执行**，
    以便不会把应用弄成装不回来的状态
64. 作为用户，我希望重置**拒绝符号链接目标**，以便不会顺着链接删掉别处
65. 作为用户，我希望重置**失败时看到原因**而不是静默失败，以便知道数据还在不在

### 打开配置文件

66. 作为用户，我希望**用系统默认编辑器打开 `settings.yaml`**，
    以便直接改配置而不需要我去翻文件系统
67. 作为用户，我希望**打开当前 profile 的 `cordis.patch.yml`**，
    以便修掉写错的补丁层
68. 作为用户，我希望**打开当前 profile 的 `package.json`**，以便查看/修正插件清单
69. 作为用户，我希望**在文件管理器里打开 profile 目录**，以便自己翻看其它文件
70. 作为用户，我希望**文件不存在时得到明确提示**，以便知道是文件没了而不是按钮坏了
71. 作为用户，我希望打开文件**不要求我先切出应用**，以便操作连贯

### 安全与边界

72. 作为用户，我希望恢复页**不能绕过 IPC 直接读写磁盘**，以便我的配置不会被网页脚本破坏
73. 作为用户，我希望恢复页**在无 Host 运行时也能用**（这正是恢复模式的核心），
   以便应用完全起不来时仍能自救
74. 作为用户，我希望**回滚/卸载失败时恢复点不丢**，以便失败的尝试不会让我更糟

## Implementation Decisions

### 技术栈（与参考实现同构）

引入 **Vite 8 + React 18 + Tailwind 4 + `@base-ui/react` + `lucide-react`**，
并**按需移植** `dsh-desktop` 手写的 shadcn 封装组件（button / card / alert / tabs /
badge / scroll-area）。不追求把参考的 13 个组件全搬。

`class-variance-authority` + `clsx` + `tailwind-merge` 提供变体与 className 合并。

> 来源确认（查 `dsh-desktop/yarn.lock`）：`@base-ui/react@1.7.0`、`lucide-react@1.41.0`
> 等**均为第三方 npm 包**；`native-ui/components/ui/*.tsx` 那 13 个文件是
> **dsh-desktop 自写**的原语封装。`dsh-desktop` 没有 `vendor/` 与 patches，未魔改第三方。

### 构建接线

- Vite 产出到独立的构建目录，`base: './'` 以支持 `file://` 加载
- **必须接入 `build:all`**——`test` 脚本依赖 `build:all`，漏接会让**干净 clone 上的
  测试失败**（ticket 02 已踩过此坑：当时 `test` 漏了 `build:flat`）
- 新增构建产物的解析函数：dev 读构建目录，打包读 `process.resourcesPath` 下对应目录
- 打包资源清单增加该目录

### 数据通道：**保留我们的 IPC，不照搬参考的 scheme**

参考实现把状态 base64 编码进 URL query，每次操作 `window.location.assign(href(...))`
**整页跳转**。我们**已经是 IPC**（`recovery-preload` 暴露 `dshRecovery.*`），
对 React 更合适：状态可直接调用、无需整页刷新。

**这是有意的差异**：视觉与结构对齐，数据通道用我们的。

### 两阶段确认（新后端）

破坏性操作走 preview → execute 两步，语义对齐参考实现的
`startup-recovery-controller`：

```
preview  →  { previewId, expiresAt }
execute  →  校验 previewId 存在 / 未过期 / 未消费 → **先消费再执行** → 结果
```

必须守住的性质：

- **有效期**（5 分钟），过期后 execute 返回 `preview-expired`
- **一次性消费**：同一 previewId 第二次 execute 必须失败（先消费再执行，
  避免执行中途失败后 preview 仍可重放）
- **数量上限**：preview 缓存有上限，防止长时间运行内存膨胀
- **目标失效**：preview 创建后目标被改动/删除时，execute 返回 `invalid-target`

### 复用阶段 3 的 checkpoint 后端

不重新实现快照逻辑。checkpoint 列表 / 差异检查 / 回滚都建立在
`createDesktopProfileCheckpoint` 之上（它已具备 3 槽轮转、skip marker、
原子替换、损坏槽容错、路径映射防静默失效）。

### 复用已有 profile 后端

profile 列表 / 切换建立在既有 `desktopProfiles` 能力之上（ticket 11 抽出的
`profile-actions-service`）。**不新建 profile 系统。**

### 能力清单（全部要做，含新建后端）

| 功能 | 后端 | 决定 |
|---|---|---|
| 插件卸载 / 恢复 / 保留隔离 | 已有 | 做 |
| checkpoint 回滚 | 已有（阶段 3） | 做 |
| profile 列表 / 切换 | 已有 | 做 |
| 诊断导出 / 启动日志 | 已有 | 做 |
| 重启 / 退出 / 返回工作台 | 已有 | 做 |
| **数据目录管理** | **新建** | 做（见下） |
| **出厂重置** | **新建** | 做（见下） |
| **打开配置文件编辑** | **新建** | 做（见下） |

**页面上不得出现假 UI**：任何暂时不可用的能力必须显示明确说明并说明原因，
而不是渲染一个点了没反应的按钮。

### 数据目录：新建概念（不是"暴露已有能力"）

实测确认我们**没有**任何数据目录概念——路径写死在
`resolveProfileRoots()` 里（`DSH_HOME ?? ~/.dsh`）。参考实现对应后端约 360 行。

**解析优先级（三态，对齐参考实现）**：

1. `environment` —— `DSH_HOME` 显式设置时优先，且**视为用户接管、只读**
2. `desktop` —— 用户在恢复页里选过的目录（记在 userData 下的状态文件）
3. `default` —— `~/.dsh`

**为什么环境变量优先级最高**：用户显式设了 `DSH_HOME` 就该尊重；
否则恢复页改一次目录会让人以为环境变量失效了。

**生效机制（关键决策）**：把这条优先级**做进 `resolveProfileRoots()` 内部**，
而不是靠写 `process.env.DSH_HOME`。

理由（实测支撑）：`resolveProfileRoots()` 是**唯一汇聚点**——`main.ts`、
`profile-actions-service`、`desktop-host`、`safe-mode` 全部经它解析，
且真实调用都传 `{ stateDir }` 不传 `home`。改这一处即可让**所有下游同时跟上**。
反之若只改环境变量，一旦哪条路径没读到它，就会出现"改了目录但仍在读旧目录"的
**静默失效**——与阶段 3 的路径映射陷阱同类，且阶段 2 我已经因为漏设 `DSH_HOME`
导致隔离完全失效过一次。

**切换流程的约束**：

- 目标必须绝对路径、**存在、且是真实目录**（拒绝符号链接，与阶段 2/3 一致的安全边界）
- **不迁移数据**——只改指向。页面上必须说清"数据不会自动搬过去"
- **不立即生效**：写完状态后需重启（与 profile 切换同构）
- 拒绝危险目标：文件系统根、当前 userData、以及任何**包含受保护路径**的目录
- 操作期间加锁，防并发与连点

### 出厂重置（破坏性最强，安全检查先行）

参考实现的安全检查**逐条对齐**：

- 拒绝重置**文件系统根**（与 `parse(target).root` 比较）
- 目标必须是**真实目录**（非符号链接）
- 拒绝重置**包含受保护路径**的目录（例如 userData 在数据目录内时，
  重置会把应用自身状态一起删掉）
- 确认流程**明确告知不可逆**——这是两阶段确认最该用的场景

**实施顺序要求**：先把检查与确认做对、测透，**再谈 UI**。

### 打开配置文件

用系统默认程序打开（`shell.openPath`）：数据目录下的 `settings.yaml`、

**文件不存在时给明确提示**，不静默失败。

### 启动流程的既有约束（不得回退）

- **恢复模式下不启动 Host**（阶段 5 已实现）。恢复页必须在此前提下可用——
  这正是它的存在意义。任何 UI 改动不得引入"恢复页依赖 Host"的假设。
- **恢复页的数据通道必须与 Host 无关**：现有 8 个恢复 IPC 均不依赖 DSH server，
  新增的 checkpoint / profile / 数据目录 / 出厂重置 IPC 也不得依赖。


### 分步实施（每步独立可验证、可提交）

1. **构建链打通**——只交付"可加载的最小页面"，**不写任何业务 UI**。

2. **UI 原语层**——`cn()`、按需移植的组件、Tailwind 主题变量与既有色板对齐。

6. **接线与清理**（替换旧页、删除旧实现、文档收尾）。

## Testing Decisions

### 什么算好测试

只测**外部行为**，不测实现细节：喂入输入、断言可观测结果。不断言"某函数被调用过"
或"某个 className 出现在 DOM 里"。

### 测试缝（沿用现有缝，不新开）

实测仓内 33 个测试**绝大多数是纯 node、零 electron 依赖**——Electron 触点全部注入。
阶段 4（重启编排）与阶段 5（启动决策）已按此写好，因此**那两块能在裸 node 下测**。

**本阶段的缝保持不变**：业务逻辑做成纯函数 / 不 import electron 的模块，
Electron 与文件系统通过参数注入。**不引入 vitest / jsdom 等第二套测试栈。**

### 要测的模块

- **两阶段确认的 store**（最有价值）：过期、重复消费、目标失效、数量上限、
  并发 execute。全部是纯逻辑，可在裸 node 下测透。
- **checkpoint 的 IPC 投影**：槽位视图（含空槽、损坏槽）→ renderer 安全形状的映射。
  可复用阶段 3 的临时目录夹具。
- **恢复页数据契约**：主进程提供给页面的快照形状，断言"损坏槽不影响其它槽"等
  已由阶段 3 保证的性质在投影层仍然成立。

### 明确不测的部分

- **不做 React 组件渲染测试**（不引入 jsdom / testing-library）
- **不做视觉回归测试**（无参考构建产物可比对）
- **构建链本身不做单测**，靠"两条路径都能加载"的**人工/脚本实测**验收
  （与 `dev-mode-paths.test.ts` 的思路一致：断言产物存在与路径正确，而非测构建器）

### Prior art

- `test/profile-checkpoint.test.ts` —— 临时目录夹具 + 往返测试（本阶段的 IPC 投影测试沿用其夹具思路）
- `test/restart-service.test.ts` —— **注入式**纯逻辑测试（本阶段两阶段确认测试的同构范本）
- `test/launch-mode.test.ts` —— 纯函数决策矩阵测试
- `test/dev-mode-paths.test.ts` —— 断言构建产物存在与路径正确

## Out of Scope

- **Safe Mode 的 UI 接线**——阶段 2 已实现隔离环境，但把它接进恢复页 UI 不在本阶段
- **React 组件渲染测试 / 视觉回归测试**——不引入第二套测试栈

- **上游依赖的大版本升级策略**——引入后只保证锁定版本可构建

## Further Notes

### 已知风险

1. **规模**：参考实现仅窗口 + 控制器就 1300+ 行，`App.tsx` 263 行密集 JSX。
   必须分步提交、每步验证，不要一次做完。
2. **视觉对齐的验证手段有限**：可以渲染**我们自己的**页面截图，但与参考实现的
   逐像素对比**需要用户提供参考截图**——无法渲染参考的 React 构建产物。
3. **依赖面扩大**：启动器从 2 个运行时依赖变成"启动器 + 一整套前端工具链"。
   实施时必须确认新装的 `react-dom` 与 `devDependencies` 里既有的 `react ^18.2.0`
   版本一致，避免一次装出两个 React 版本。
4. **构建产物与测试的耦合**：`test` 依赖 `build:all`，因此**构建链必须一次接对**，
   否则会污染一个目前全绿的测试基线（当前 406 / 400 / 5）。
