# 阶段 6 实施顺序决策（为什么 07 先于 01）

> 用户让我"按最优路线来"。这是决策与理由。

## 结论

```
07 数据目录后端  →  08 出厂重置  →  09 打开配置   →  01 构建链  →  02,03,04 → 05 → 06
```

原计划是 01（构建链）先做。**改为后端三件套先做**，理由如下。

## 理由一：风险不对称

| 候选先做 | 风险性质 | 出错后果 |
|---|---|---|
| **01 构建链** | 引入新工具链 | **会污染现有 406/400/5 基线**（`test` 依赖 `build:all`） |
| **07 数据目录** | 纯后端逻辑、可注入、裸 node 可测 | 只影响新代码本身 |

构建链现在是**唯一会让"全绿基线变红"的改动**——它改 `package.json` 的
`build:all` 与 `extraResources`，一旦接错，所有测试都会失败。而 07 是**加法**：
新增模块 + 新增解析分支，不碰现有测试路径。

**先把加法做完，把唯一的"会弄脏基线"的改动留到有完整验证精力时做。**

## 理由二：07 会改变 01 的部分前提

07 要让 `resolveProfileRoots()` 消费数据目录状态。这意味着恢复页**运行时的
数据目录可能不是 `~/.dsh`**。

如果先做 01（构建链 + 最小页面），最小页面会照"数据目录就是 `~/.dsh`"的心智模型写；
等 07 落地后再回头看，可能发现页面/解析路径的前提要调整。

**先定数据模型，再做消费它的界面**——这是更自然的顺序。

## 理由三：07/08 是第 5 阶段性质的自然延续

`resolveProfileRoots()` 的改动与阶段 5 的"启动时消费标记"是**同一类工作**：
都是"启动期解析一个决定运行时行为的输入"。我刚刚做完阶段 5，
对这块的心智模型最热——**趁着上下文还热做它，比切换到全新工具链再切回来成本低**。

## 理由四：危险操作先于 UI

08（出厂重置）有 4 条安全拒绝条件，必须**在无 UI 干扰下测透**。
一旦先做了 UI，调试时会被"这个按钮为什么没反应"干扰，
而那时问题可能出在 UI、IPC 或安全断言三处中任意一处。

## 为什么不是 07 与 01 并行

技术上可以（互不依赖），但：
- 两者都会改 `package.json`（01 改 `build:all`/`extraResources`，07 不改）
- 01 需要"干净基线"作为验收标准，而并行的另一条改动会干扰这个判断
- **串行 + 每步独立验证**是本项目一贯做法（阶段 1–5 都是这么走的，效果良好）

## 调整后的 ticket 依赖

`07/08/09` 原本 `Blocked by: 03`（03 是"API 层 + checkpoint/profile 接线"）。
但 07 的后端**不依赖 03 的任何产出**——它只依赖现有的 `resolveProfileRoots()`。

**修订依赖**：

```
07  ← 无（只依赖现有 resolveProfileRoots）
08  ← 07（出厂重置复用数据目录解析）
09  ← 无（只依赖现有 profile 解析）
01  ← 无
02  ← 01
03  ← 01
04  ← 03
05  ← 02, 04, 07, 08, 09
06  ← 05
```

这样 07 可以立即开始，不被 01/03 阻塞。

## 每一步的验收标准（不变）

- `check:all` 通过
- 全量测试**不劣于 406 / 400 / 5**
- 每条安全性质做**反向验证**（去掉保护后测试必须失败）
- 需要出包验证的步骤（01/06）必须实测 **dev 与打包两条路径**
