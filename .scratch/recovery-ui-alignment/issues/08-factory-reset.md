# 08 — 出厂重置（新建后端，破坏性最强）

**What to build:** 出厂重置——把数据目录清空、回到初始状态。含完整安全检查。

**Blocked by:** 07

**Status:** ready-for-agent

## 为什么安全检查必须先于 UI

这是**破坏性最强、最难挽回**的操作。参考实现单独用一个模块
（`desktop-factory-reset.ts`，105 行）做**安全断言**，而不是把检查散在业务代码里。

**实施顺序要求：先把检查与确认做对、测透，再谈 UI。**

## 逐条对齐参考实现的拒绝条件

参考实现的 `assertDesktopFactoryResetTarget` 有 4 条检查：

- [ ] **拒绝重置文件系统根** —— 与 `parse(target).root` 比较，防误删整块盘
- [ ] **目标必须是真实目录** —— `lstatSync().isDirectory()` 且**非符号链接**
- [ ] **拒绝重置包含受保护路径的目录** —— 用 contains 判断；
      例如 userData 若在数据目录内，重置会把应用自身状态一起删掉
- [ ] **检查 profiles 子目录的存在性**（决定重置的实际影响面）

**这四条一条都不能少。** 每条都要有对应的单测与**反向验证**。

## 交付物

- [ ] 安全检查函数（独立模块，纯逻辑，不 import electron）
- [ ] 重置执行流程
- [ ] **两阶段确认**：先预览（显示数据目录、将清除的 profile 数量）再执行
- [ ] IPC：预览 / 执行

## 必须守住的约束

- [ ] 预览必须**明确告知不可逆**
- [ ] 执行前再次校验目标（预览与执行之间目标可能变了）→ 返回 `invalid-target`
- [ ] 复用 ticket 04 的两阶段确认机制，**不另造一套**
- [ ] 失败时**不留下半清除状态**的能力边界要说清（能保证什么、不能保证什么）

## 验收

- [ ] 单测覆盖：四条拒绝条件、预览过期、预览后目标被改动、执行失败
- [ ] **反向验证**：逐条去掉安全检查，对应用例必须失败
- [ ] 全量测试基线不变（406 / 400 / 5）

## 不做

- 不做数据迁移/备份（重置就是清空）
- 不接 UI（ticket 05）
